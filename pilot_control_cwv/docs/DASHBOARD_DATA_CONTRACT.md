# Dashboard Data Contract

## Purpose

This document defines the JSON snapshots the dashboard should read.
These snapshots should be generated by the existing pilot KPI reporting pipeline
so the dashboard, workbook, and email all reflect the same numbers.

## Design Rules

- one daily snapshot set per report date
- no raw spreadsheet parsing in the frontend
- every snapshot includes source freshness metadata
- every metric carries:
  - pilot values
  - sister values
  - baseline values where applicable
  - trend series
  - status

## Output Location

Recommended output root:
- `/Users/mark/Property_Analytics/pilot_control_cwv/reports/dashboard_snapshots/YYYY-MM-DD/`

Recommended files:
- `overview.json`
- `cwv.json`
- `traffic.json`
- `funnel.json`
- `properties.json`
- `archive.json`

## Calculation Guidance

### Rollups

Use simple averages for v1:
- `pilot_current` = average of current pilot pair values
- `sister_current` = average of current sister pair values

### Gap Status

Recommended logic:
- `closed`: pilot is at or better than sister
- `closing`: pilot-sister gap shrank over trend window
- `widening`: gap grew
- `stable`: gap unchanged within tolerance
- `mixed`: conflicting metric family signals

### Display Formatting

- CWV scores: integer or one decimal as needed
- BI / Heap rates: percentages
- dates: `M/D`

## Contract Stability

The dashboard should depend on these JSON contracts, not on:
- workbook layout
- spreadsheet headers
- direct database schema in the browser

That allows the reporting pipeline to absorb source complexity once.
