# Captain Memory And Directive Standard

Status: Draft v1
Date: 04/28/2026
Owner: MarketingOps / Property Analytics
Scope: Memory model and directive requirements for Captain's Log, Captain's Brief, Admiral Read, and Commodore memory

## Purpose

A Captain is not a report generator.

A Captain owns the property's operating intelligence, remembers its history, learns from prior decisions, and converts the current evidence set into a useful directive.

For The Pointe Bentonville, Captain Benton must be able to explain what changed, why it matters, what was expected, what was learned, and what must happen next to recover the property.

The Captain is expected to be actively aware and engaged in the life of the property. The Log is not a static reporting archive; it is the Captain's working reality model for the property.

The Captain is also accountable for the support team. The Quartermaster, Navigator, Signals Officer, Engineer, Boatswain, Logkeeper, First Officer, and any additional specialist agents may own lanes, but the Captain must know whether they have done their jobs and whether their outputs are sufficient for a reliable property directive.

## Captain Memory Layers

| Layer | Job | Examples |
| --- | --- | --- |
| Truth Memory | Current and historical facts from governed sources | occupancy, exposure, guest cards, leases, cancellations, concessions, unit aging, GA4, GSC, GBP, paid media |
| Decision Memory | Human or Captain decisions and the reason behind them | pricing decisions, concession approvals, source shifts, content priorities, package changes |
| Action Memory | Open and closed work with owner, due date, expected lift, and proof | web tickets, pricing tests, follow-up audits, GBP posts, ad spend changes, make-ready pushes |
| Support-Team Memory | Status and quality of assigned support lanes | Quartermaster blocked by source arrival, Navigator stale after site change, Engineer EVS failure unresolved |
| Pattern Memory | Repeated property behavior observed over time | A1 pressure repeats, Website abandonment, Google source quality, review theme recurrence |
| Learning Memory | What the Captain expected and whether reality confirmed it | recommendation worked, traffic did not convert, spend was wasted until make-ready cleared |
| Specs Memory | Structural expectations and drift between Specs and live property reality | homepage sections, metadata, schema, HTML/content requirements, reusable copy rules, page component gaps |
| Doctrine Candidate Memory | Property lesson that may matter across properties | tactic or threshold worth promoting to Commodore/Fleet/Ledger review |

## Captain Log Entry Requirements

Every meaningful Captain's Log entry should preserve:

- what was true at the time
- what changed since the prior read
- what the Captain believed or expected
- what action was recommended
- who owned the action
- what happened afterward
- what the Captain learned
- whether the learning stays local, rises to Commodore memory, or becomes a Ledger candidate

The entry should be evidence-backed. If the entry is a human note or strategic judgment, it should say that plainly.

## Required Directive Questions

For a recovery property, the Captain must be able to answer these questions in the Captain's Brief or Admiral Read.

1. What happened in the last 30 days that caused occupancy decline or exposure increase?
2. How many net move-ins or exposure reductions are needed to get below the target ATR/exposure threshold?
3. What traffic volume is required to reach those move-ins in the target window?
4. Which sources should produce that traffic, and how much should each source contribute?
5. Should the property adjust pricing, adjust concessions, increase advertising, shift spend, or fix operations first?
6. How have each of the major sources performed, and what spend or source shift is recommended?
7. What urgent website improvements should be made, including exact on-page copy recommendations when content is part of the resolution?
8. Where does the live page/content/HTML drift from Specs, and which Specs-backed changes are urgent?
9. What are the three strongest unique selling propositions for the property right now?
10. Do GBP and website images support the positioning, or should a human review be assigned?
11. What do the most recent reviews say, including sentiment, concerns, and action items?
12. Are make-readies a constraint on recovery?
13. Are hold times or GC-to-move-in timelines a constraint on recovery?
14. Is there a people/process issue, such as closing ratios, follow-up, abandonment, or application handling?
15. Would an effective-rent / lower-concession posture differentiate the property in the market?
16. What exact 30-day recovery plan should be executed, with owners, dates, expected lift, and measurement sources?
17. Which support lanes are current, stale, blocked, or failing to produce action-ready intelligence?

## Directive Format

The Captain's output should not be a data dump.

Each major section should resolve to:

- Read: the Captain's interpretation
- Evidence: the governing facts and source references
- Directive: the action, owner, due date, expected effect, and measurement source
- Memory: what should be remembered for the next cycle

Website, content, SEO, and AI-visibility sections must use a five-part grounding chain:

- Specs standard: what the page/content/HTML is supposed to be
- Live reality: what the current site or public surface actually shows
- External evidence: DataForSEO, GSC, GA4, GBP, PSI, reviews, or other observed performance signals
- Directive: the exact page/content/HTML/action change
- Follow-up proof: the source that will prove the change worked

## Commodore Communication

The Commodore receives recurring Captain updates and maintains portfolio or regional memory.

The Captain should send a Commodore update when:

- a threshold is crossed
- a recovery plan is launched
- a recommendation materially changes
- a tactic succeeds or fails
- a property pattern may apply to other properties
- a source or operating gap blocks a confident read

The Commodore stores:

- cross-property patterns
- repeated source or operational failures
- tactics that worked or failed
- Captains needing attention
- lessons that should be promoted to Fleet Command or The Ledger

## Promotion Rules

Memory should move upward only when it earns the trip.

| From | To | Promotion Trigger |
| --- | --- | --- |
| Captain's Log | Commodore Memory / Fleet Brief | A property lesson may apply to a region, cohort, market, or similar condition |
| Commodore Memory | The Ledger | A repeated lesson becomes durable doctrine or an approved operating rule |
| Captain's Log | The Ledger Candidate | A single-property event is severe, highly instructive, or policy-relevant |

All promotions must keep lineage back to the original evidence and Captain's Log entry.

## Quality Bar

A Captain with passion for perfection does not publish:

- unsupported claims
- vague recommendations
- hidden source conflicts
- generic "monitor closely" language
- action plans without owners
- action plans without expected effect
- advice that ignores prior failed attempts
- a fresh conclusion that forgets the property's history
- a directive that cannot be measured
- website recommendations that ignore Specs
- SEO/content recommendations without exact copy, page, or HTML/action detail when the evidence supports specificity
- a Brief that hides stale or missing support-lane work
- a recovery plan that does not assign follow-through to the correct support role or human owner

## Memory Boundary

Memory is not truth by itself.

Data Pond governs facts where a governed source exists. Captain memory preserves interpretation, decisions, actions, lessons, and history. When memory conflicts with current source-of-record facts, the Captain must reconcile the conflict rather than repeat the older memory.
